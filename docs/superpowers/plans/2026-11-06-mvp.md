# writing-styles-from-giants MVP implementation plan

Status: proposed sequence, not an executed product plan. Repository-management files exist; the production catalog does not. See [PROJECT.md](../../PROJECT.md) for requirements and [REFERENCE.md](../../REFERENCE.md) for the structural reference.

**Goal:** Deliver one source-reviewed English/Korean method with explicit selection, observable levels, and a tested installation path, then expand from evidence. The six named hosts remain targets; the first release reports only tested combinations.

**Approach:** Portable method content first. Reuse the host's model and an existing installer. A custom runtime, CLI, plugin manifest, or adapter is conditional on a documented gap, not a prerequisite.

## Task 1: Author one complete method

Files: create the first real `skills/<method-id>/` directory and source-linked cases under `evals/`; extend `scripts/check_repository.py` and `tests/test_repository.py` for the actual catalog when needed. Do not add an empty production skill or runtime package scaffold.

- [ ] Choose a source after provenance/rights review; record exactly what was read.
- [ ] Write concise agent steps, method data, per-level rules, exceptions, and en/ko variants using the [authoring contract](../../METHOD_AUTHORING.md).
- [ ] Add ordinary-use, important-exception, and meaning-preservation cases, including uncertainty and conditions. Have each language adaptation reviewed.
- [ ] For new validator logic, add behavioral tests for valid content, broken references, duplicate IDs, mismatched locales/versions, and disabled invariants.
- [ ] Add matching README catalog entries linked to the real `SKILL.md`, with intended use, locale status, and limitations.

Done when the directory is complete, the cases and review evidence are present, and repository checks pass. A model evaluation record is required before `reviewed` status; the example cases alone do not establish it.

## Task 2: Verify selection and level behavior

Files: update the method workflow and source-linked evaluation cases. Add a separate router skill only when real method choices require it; add runtime code only when a skill workflow cannot meet the selection contract.

- [ ] Exercise explicit selection, opt-out, `light`/`standard`/`strict`, and unavailable or experimental locales in a host.
- [ ] Check that facts, units, negation, conditions, exceptions, uncertainty, quotations, citations, and code survive every level.
- [ ] Record host/model/version, prompts, method/locale/level, outputs, failures, and judging process. Keep model evaluation separate from repository checks.
- [ ] When recommendations are introduced, cover fit explanations, explicit override, incompatible combinations, and no silent English fallback.

Done when actual runs support the claimed method behavior and disclose unresolved cases. Do not infer automatic activation from file discovery.

## Task 3: Evaluate existing installation and host support

Files: update [COMPATIBILITY.md](../../COMPATIBILITY.md), the installation guidance in both READMEs, and any narrowly needed fixtures/tests.

- [ ] Evaluate an existing installer in temporary project roots against the [installation contract](../../ARCHITECTURE.md).
- [ ] Test complete references, project/global choice, durable symlink or disclosed copy behavior, existing files, modified copies, paths with spaces/Korean, shared roots, interrupted updates, and removal preservation.
- [ ] Test discovery, explicit invocation, and reference access for each claimed host/version/OS. Keep unavailable hosts `planned` or `docs-confirmed`, with the actual evidence.
- [ ] If a required behavior is missing, document the gap and propose the smallest fix. A custom CLI or adapter needs a focused design and filesystem behavior tests before implementation.
- [ ] Add an installation command only after a real catalog and verified delivery path exist. Avoid duplicate plugin/skill installations.

Done when installation and removal work without damaging user content on the claimed matrix. A project-owned npm package is optional.

## Task 4: Prepare a source release

Files: update README catalog entries, compatibility evidence, CHANGELOG.md, VERSION, and workflows only as needed for the delivered content.

- [ ] Run repository checks and the recorded method/locale/host evaluations; resolve meaning-preservation and installation ownership failures.
- [ ] Verify archive contents and rights notices. Confirm the hosted CI and source-release workflow, repository protection settings, and maintainer release authority.
- [ ] Follow [RELEASING.md](../../RELEASING.md) to create a draft source release from reviewed `main` and inspect it before publication.

Changesets, npm publishing, native plugin bundles, and additional categories wait for a demonstrated distribution need. This plan does not authorize remote publication or global installation.
